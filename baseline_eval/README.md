# 先验证原版，再验证改版

这套工具针对 wandz53/deepsearch-agent 的 `app/agent/main_agent.py` 制作。它直接调用原有 `run_deep_agent(question, session_id)`，不需要启动后端服务或前端，也不修改主 Agent 的提示词、工具列表和调度逻辑。只在独立评测进程中附加记录器。

它验证的是主 Agent 执行能力，不包含网页、HTTP、WebSocket 的端到端测试。附加记录器有少量开销，两个版本都应使用同一份脚本。文件里的评分标准不会传给 Agent。

## 1. 放到哪里

将 ZIP 解压得到的 `baseline_eval` 文件夹复制到你本机项目根目录，与 `app`、`pyproject.toml`、`uv.lock` 同级。

先保留当前原版代码。此时不要应用 Reviewer 等功能补丁。可以提交一次当前代码作为基线；评测会记录 commit 和文件 SHA256，但不会替你提交、打标签或推送代码。不要只依赖 README 描述来区分版本。

在 VS Code 打开整个 `deepsearch-agent` 文件夹，再打开终端。下面所有命令都在项目根目录执行。

## 2. 先准备环境

项目要求 Python 3.12。若已有可用项目环境，沿用现有环境即可。项目使用 uv 时运行：

```bash
uv sync --frozen
```

如果终端提示找不到 uv，请先安装 uv；如果你原本用虚拟环境和 pip 运行项目，可在原有已安装项目依赖的 Python 3.12 环境里把下面的 `uv run --frozen python` 换成 `python`。

若根目录还没有 `.env`，复制项目的 `.env.example` 并重命名为 `.env`，填写真实配置。不要覆盖已有可用配置。模型配置使用项目原有的：

```dotenv
OPENAI_BASE_URL=你的模型服务兼容接口地址
OPENAI_API_KEY=你的模型服务密钥
LLM_QWEN_MAX=你的模型名称
TAVILY_API_KEY=你的Tavily密钥
```

本轮 T01 需要实际可用的模型及 Tavily 服务。原版模块也会在导入时创建 RAGFlow 客户端，因此保留项目原有的 RAGFlow 配置；如果在初始化时报错，先按 `console.log` 解决。三道题不要求 MySQL/RAGFlow 数据服务，但原版 Agent 仍可能自行调用这些工具；这种行为会被如实保留，脚本不会偷偷移除工具或伪造服务。

依赖安装失败与 API 鉴权失败属于环境问题，不是模型内容能力得分。包内没有提供 API 密钥，也没有预先跑出的真实 Agent 成绩。

## 3. 第一次怎样运行

先预览题目，不调用模型、不消耗 API：

```bash
uv run --frozen python baseline_eval/run.py --dry-run
```

建议先跑一道固定数据题，确认附件读取、计算、文件生成和记录链路：

```bash
uv run --frozen python baseline_eval/run.py --label smoke --case T02
```

看终端打印的结果目录，检查 `T02_r1/console.log` 和 `artifacts/`。这次是试运行。环境通了之后，正式跑原版三题：

```bash
uv run --frozen python baseline_eval/run.py --label v0
```

脚本逐题执行，每题使用新进程和新会话，不把前一道题的会话记忆带入下一题。默认每题最多300秒；网络较慢可以给两个版本都使用 `--timeout 600`。超时会保存已有记录，不能据此认定题目内容正确。

如果第一题初始化失败，脚本会停止，避免连续重复同一种环境错误。后续未运行题目在 `not_run.json` 中，不会被当作已通过。

## 4. 究竟跑什么题

完整原文在 `cases.json`，脚本自动提交，不需要你复制到网页。

| 题号 | 给 Agent 的任务 | 主要验证点 | 必须产出 |
|---|---|---|---|
| T01 | 联网比较地震预警与破裂反投影成像，回答4个维度并给出至少3个支持正文的来源URL | 搜索、研究、引用、整理 | T01_research.md |
| T02 | 读取虚构公司附件，计算收入增长、研发占比、员工增长 | 附件读取、计算、Markdown/PDF交付 | T02_analysis.md、T02_analysis.pdf |
| T03 | 面对只有2024年出货量、2025年销售额的材料，回答增长率与净利润 | 识别统计口径不一致、信息不足、避免编造 | T03_limits.md |

T02人工核对答案：25%、12%、25%。T03应该说明两个问题均缺乏足够数据，不能把出货量与销售额直接比较，也不能把销售额当净利润。T01需要你逐条核查来源与正文，URL存在不代表它支持结论。

T01是实时网络测试：即使同一题，搜索结果也可能变化。因此不能把所有提升都归因于代码。T02/T03的输入文件固定，更适合初步对比推理和文件交付。这3题是起步检查，不能支撑“通用Agent准确率”的结论。

## 5. 内容和数据保存在哪里

每次运行会创建新目录，例如 `baseline_eval/results/v0_日期时间_随机后缀/`，不会覆盖旧结果。终端会打印完整路径。

| 文件/目录 | 保存内容 | 怎样使用 |
|---|---|---|
| manifest.json | 题目、代码commit、代码哈希、依赖版本、附件哈希、重复次数、超时配置 | 说明测试的是哪个版本、哪套题 |
| summary.md | 人能直接阅读的汇总表 | 先看运行状态和缺失内容 |
| summary.json | 结构化的批次和逐题指标 | 后续做图表、统计或导入分析程序 |
| not_run.json | 未运行的题号和轮次 | 识别中断、不完整批次 |
| T02_r1/input.json | 实际问题、会话ID、轮次 | 复核这次输入 |
| T02_r1/inputs/ | 本题固定附件副本 | 保留输入证据 |
| T02_r1/answer.md | 最后一次主Agent结果事件中的回答 | 检查最终回答；未收到回答则不创建 |
| T02_r1/artifacts/ | 会话目录中的文件副本，包含输入附件与实际生成文件 | 打开Markdown/PDF核对 |
| T02_r1/console.log | 完整控制台输出和异常栈 | 排查初始化或执行问题 |
| T02_r1/monitor_events.jsonl | 原版monitor的结构化事件 | 查子Agent调度、最终回答、错误事件 |
| T02_r1/trace.jsonl | 收到的工具输入/输出、父子调用ID、模型用量事件 | 找到错误发生在哪一步 |
| T02_r1/search_results.json | internet_search工具实际返回的原始内容及查询输入 | 对照来源证据；未调用搜索时是空列表 |
| T02_r1/model.json | 暴露出的模型名称、温度、输出上限 | 对照两次运行配置 |
| T02_r1/result.json | 耗时、调用观察次数、Token、运行状态、指定文件是否存在 | 自动统计的原始数据 |
| T02_r1/scores.json | 人工评分及依据 | 将内容质量转换成可复核的数据 |

每一行 JSONL 是一条事件。不要只保存最终截图：截图无法还原工具返回了什么。搜索记录保留工具当时的返回值，不等于网页完整快照；若T01要用于正式成果，另行保存核查过的关键证据和访问日期。

`total_tokens` 只有收到的每次模型调用都有用量时才填写，否则是 `null`。`observed_total_tokens` 是已收到用量的小计。它们不能覆盖不可见的服务端重试、其他服务费用；这里不虚构金额成本。工具调用次数也只是回调观察值；工具返回错误字符串可能不会触发异常回调，所以“工具错误数为0”不代表全部工具结果有效。

`returned_with_answer` 只表示函数返回且收到回答；`error_event` 表示原版上报过错误；`returned_without_answer` 表示没有收到最终回答。内容是否正确以评分为准。`parent_wall_seconds` 包含初始化时间；`agent_seconds` 只计主函数运行，超时可能没有完整值。

运行数据目录已在本工具的 `.gitignore` 中排除，避免原始记录混入代码提交。完成一批后，请把整个批次目录压缩备份到自己的项目资料目录；保留其中的评分、原始证据和manifest。对外展示前检查日志是否包含服务返回的敏感信息。

## 6. 怎样人工评分，再自动汇总

打开每题 `scores.json`，每项 `passed` 初始为 `null`（未评分）。逐项对照回答、文件和来源，把它改成 `true`（通过）或 `false`（不通过），并填写 `evidence_or_reason`。布尔值不加引号。不要把看起来合理直接等同于通过。

例如T02收入计算正确：

```json
{
  "id": "revenue",
  "criterion": "营业收入同比增长率为25%，计算为(10-8)/8，年份和单位正确",
  "passed": true,
  "evidence_or_reason": "T02_analysis.md收入分析段写明(10-8)/8×100%=25%"
}
```

改完3题后重新汇总。把引号内路径替换为终端实际打印的批次目录：

```bash
uv run --frozen python baseline_eval/run.py --summarize "baseline_eval/results/v0_实际目录名"
```

这一步只读本地结果，不调用模型。每题人工分为通过评分项数/总项数；全部要求通过、收到正常回答且指定文件存在时，该题才计为全部通过。未评分保留空值；已确认执行失败计为不通过。批次未跑完或尚有待评分项时，不输出完整批次通过率。

## 7. 改动之后如何对比

保留原版批次结果，只修改你要验证的Agent能力。不要同时更换模型、题目和评分标准。改动后运行：

```bash
uv run --frozen python baseline_eval/run.py --label v1
```

按同一评分标准完成v1人工评分，再比较：

```bash
uv run --frozen python baseline_eval/run.py --compare "baseline_eval/results/v0_实际目录名" "baseline_eval/results/v1_实际目录名"
```

比较表写入第二个批次目录。题目或附件哈希不同会拒绝直接比较。模型、温度、超时和依赖环境仍需你对照记录；工具不会自动判定所有实验条件等价。

起步时每题1次即可。确认流程后，可分别对v0/v1运行 `--repeat 3`，每个版本共9次，观察同题波动。重复运行不增加独立题目数量。正式写简历前，应扩充独立题目，并保留一部分不用于调参的测试题。

如果新增Reviewer、重试或记忆，本脚本提供整体效果的前后对比；还需针对新增能力记录“发现了哪些错误、修复了哪些、引入了哪些新错误、增加了多少调用”。不能仅凭总通过率宣称Reviewer检错率或记忆有效率。

本包已用离线替身验证记录链路、缺失用量、错误、超时及评分处理；没有使用你的API运行真实Agent。离线测试结果不是Agent能力分数。
